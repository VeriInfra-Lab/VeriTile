# Finite quant_transpose_kernel acceptance candidate, revision 1

The public statement remains `QuantTransposeFinite.quant_transpose_finite_acceptance` in `bench/tritonbench_g/quant_transpose_kernel/FiniteAcceptance.lean`. The final module list and individual successful or failed Lean attempts are recorded in `evidence/module-layout.json` and `evidence/attempts`. This revision replaces the former padded-i32 success restriction with an interpreter for the actual constexpr, i32 and i64 expression widths and actual wrapped pointer addresses. It is producer work awaiting an independent root review. `inherited-v1` preserves the preceding candidate unchanged; the included earlier peer review and native compilation evidence do not approve this revision.

The wrapper performs the complete logical-view `abs → max → unsqueeze → 1.0 / maximum` chain before exact rank-two unpacking, fresh CUDA int8 output allocation, source stride assertions, autotuning and the final return `(out, original maximum)`. Output shape `[N,M]`, strides `[M,1]`, zero offset, actual extent and allocation device are explicit. The returned maximum is the original shape-`[1]` scalar allocation, not the reciprocal. Actual host writes establish maximum and reciprocal bytes before any kernel load. The logical input view, storage offset, storage extent, physical allocation intervals, permissions and initial allocation bytes remain concrete primitive metadata.

Ordinary nonnegative Torch dimensions, strides and numel are below `2^63`. Each actual metadata argument specializes independently: value 1 becomes constexpr, other values below `2^31` become signed i32, and the remaining values become signed i64. The program id and lane ranges start at i32. Every binary expression promotes its own operands and wraps at that node's selected width; an i32 product may wrap before a later i64 addition. Constant arithmetic remains unbounded, with Python floor division and modulo when both operands are constant. Runtime signed division truncates toward zero; division by zero and signed-minimum divided by -1 are explicit interpreter observations. The original grouped formula, including `pid_m = group_id * GROUP_M + pid % group_size`, is retained with its partial-group rotation.

Pointer expressions sign-extend the selected signed offset to 64 bits, scale by element size, and add the actual pointer modulo `2^64`. Input and output access checks apply only to addresses of mask-selected lanes. The inverse load is unmasked and is checked once per program. Inactive padded arithmetic imposes no no-wrap bound. The host grid uses exact integer cdiv; a grid-x request outside the CUDA target limit is separately classified. The four reviewed singleton examples with stride `2^30` or `2^31` along either axis are included. Safe wrapped accesses that differ from mathematical tensor coordinates can also return, with their actual bytes specified.

The main theorem has no `Safe` or `ArithmeticRefines` premise. Under the ordinary `Domain` and `PhysicalBinding` inputs, it partitions the supported source into grid-limit observations, typed interpreter observations, and successful actual-address returns. The interpreter exposes `integerDivision`, `inputAccess`, `inverseAccess`, `missingInputBytes`, `missingInverseBytes`, `outputAccess`, `outputOwnershipConflict` and `conversionUndefined`. These observations assert no native exception, race winner, rollback or postfailure state. They do not assert that every constructor is reachable under the final premises: successful physical binding and host preparation rule out inverse-access and missing-inverse-byte observations.

`NativeResult` specifies a plan derived from all actual masks, input and inverse bytes, independent scalar expressions and output addresses. Execution is proved to realize that plan through concrete byte stores across every ordered program and every finite successful warmup/trial followed by the selected final launch. Every final byte has an independent last-write result; untouched output bytes retain their arbitrary allocated contents, and bytes outside output retain their host-prepared contents. Output ownership is tracked within each launch and reset between launches. The optional `ArithmeticRefines` relation separately recovers the usual mathematical transpose and its actual returned-byte formula. It is not used to exclude wrapped states from the main theorem. The existing fp32 scalar route remains linked through `FiniteLegacy`.

The source retains two distinct but identical `128×128`, `GROUP_M=8`, four-warp, three-stage autotune entries. The 22 canonical CPU/CUDA dtype profiles preserve first abs, maximum, rank, stride, signature, llrint-overload, CPU-pointer and propagating primitive failures; no input-CUDA assertion is invented. Eight CUDA storage dtypes are admitted: bool, uint8, int8, int16, int32, int64, fp32 and fp64, with Torch default float32. The inherited original-AST compilation receipt has 18 successful and 10 rejected profiles. The independent metadata receipt adds 18 mixed-width or runtime-specialized compilation records. Both receipts, their copied source prefixes, and all referenced local IR/PTX artifacts are bound by exact hashes. No GPU execution or native numerical validation is claimed.

The llrint domain remains structural: the actual produced word must decode to a finite rational whose nearest-even rounded integer lies in `[-2^63,2^63)`. NaN, infinity and rounded overflow are covered by `conversionUndefined` without a fabricated output. The 16 admitted dtype/config returned-or-undefined cases retain 140 exact numerical ports in 16 families, covering host abs/max/reciprocal, source promotions, literal 127, both multiplies, defined llrint64 and int8 narrowing. The revised table has 863 cases: the original 735 classifications plus eight structural observation classifications for each of those 16 dtype/config pairs. The 128 added observations and all value-insensitive first-error cases have zero numerical ports because they claim no intermediate numerical equality or postfailure memory. Numerical deferral cannot waive a structural issue.

`propose.py` produces the scope, declaration and exact numerical authority proposals. `authority_adapter.py` requires both an independently reviewed package receipt and a separate root-review hash. It checks current modules, the frozen `.lean.txt` mapping, every dependency snapshot, project source hashes, both native receipts and all retained native artifacts. Only repository sources and retained checkpoint materials become queue authority inputs. Historical project/external object paths are checked during producer verification and retained as evidence; CI does not depend on those local paths. `check_adapter.py` uses an explicitly synthetic review fixture, preserves previous authority, checks unchanged whole-queue equality, rejects every one-port omission, and exercises receipt/review/source/native/dependency/self-review mutations. Its results authorize no acceptance.

Repository/Git and the inherited v1 candidate remain unchanged by these proposal edits. Integration still requires root's independent substantive review and exact queue/catalog/ledger updates. The accepted-program count increment remains zero until that review and integration are complete.
