Focused independent review of unconditional pointer metadata in frozen vector native revision2 and custom native revision1. No concrete loss of a pre-extraction failure path was found. This audit clarifies the interpretation of total metadata fields; it does not replace either package's independent source review or modify its numerical authority.

`TensorBinding.extractedPointer` is equality between two total metadata fields. Neither that field nor `mappedData` asserts a native `Result.ok`, accessibility permission, or successful pointer extraction. On a path that does not consume the native pointer because allocation is followed by a CUDA assertion, rank-zero error, context/signature/compilation error, signed-grid parse error, or pointer-packing error, the absent pointer result can be completed arbitrarily while satisfying the ordinary equations. On a genuinely successful extraction path, the metadata must still use the actual extracted pointer; the completion argument cannot justify replacing a successful translated pointer with raw data_ptr.

A concrete completion for the tested unconsumed cases takes `kernelArgumentPointer = buffer.data = torchDataPointer`, `buffer.base = torchStorageBase`, actual capacity and owner, and both permission functions constantly false. For a nonempty tensor, raw data_ptr already equals storage base plus storage offset times element width; for an empty tensor, the equation selects zero independently of the underlying storage span or offset. Fresh `empty_like` output storage supplies both freshness clauses, including when inputs alias each other. Actual preserve-format output strides are retained. Thus positive offsets, CPU tensors, empty null pointers, and lack of launch-device permissions do not create an inconsistency.

The review read both frozen `NativeCorrect.lean` modules and their arithmetic/memory boundaries. The successful branch uses native addresses under the already reviewed ordinary typed-memory interpretation. This audit did not reopen that boundary or infer a new successful mapping on a failing path. The wording “actual successful extractPointer result” should be understood as “actual on successful extraction, arbitrary unconsumed total completion when extraction is absent or fails.” Making that conditional interpretation explicit is a documentation clarification; unused unconditional fields alone are not an acceptance blocker.

`witness.py` checks the corresponding arithmetic/metadata/freshness equations on five real CPU allocations: a float32 view with storage offset three; a rank-zero tensor; shape `(2^35, 0)`; a canonical fnuz dtype; and an empty view with offset 1,000,000 over nonempty storage. `cpu-results.json` contains the actual metadata and proposed completions. These are satisfiability witnesses, not Lean proofs for every Torch allocation. They execute no CUDA pointer extraction, GPU work, kernel values, or native failure path; stage labels identify which modeled failure paths motivate each witness. The source-level reasoning above, rather than mere sampling, explains why equality to a free field does not imply success.
