## Revision 2 staging boundary

Revision 1 and its independent counterexample remain frozen separately. The old stage gathered every current checkpoint file, so a file added after final validation could enter staging without belonging to the validation seal. Revision 2 requires exact equality with the sealed checkpoint paths plus `validation.json` before staging, permits only the newly created `staging-review.json` afterward, and uses `--no-renames` for literal path-set comparisons. No source integration, validation command, numerical predicate, protected pin, dependency, required build or expected count changes.

Staging does not auto-reset or roll back. Failure after `git add` may retain index changes; a direct retry is blocked until root reviews an explicit repair. Existing staging reviews are retained and block duplicate execution. The focused stage controls use fresh `/tmp` files and in-memory Git simulations only; they never run a Git mutation or claim actual source acceptance.
